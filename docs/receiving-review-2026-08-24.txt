ارزیابی بخش دریافت AnbarSYS
تاریخ بررسی: 2026-08-24

مبنای نسخه GitHub

این گزارش پس از git fetch --prune و بررسی مستقیم آخرین شاخه‌های منتشرشده در origin بازبینی شده است. نسخه‌های مبنا:

- storemesh-platform: origin/feat/addendum-01-fix-request-07 @ 8681403
- storemesh-site-server: origin/feat/addendum-01-fix-request-07 @ 34e209e
- storemesh-web: origin/feat/addendum-01-fix-request-07 @ 1603cc6
- storemesh-terminal: origin/feat/operations-completion-round-3 @ abbe707
- storemesh-pda: origin/feat/operations-completion-round-3 @ 52a459f
- storemesh-contracts: origin/feat/addendum-01-fix-request-07 @ 2b48758

این شاخه‌ها جدیدتر از origin/main هستند. بنابراین گزارش درباره آخرین کد موجود روی GitHub است، نه main قدیمی. مقایسه هر ورک‌تری با ref ریموت متناظر، به‌جز خود فایل‌های گزارش، هیچ اختلاف کدی نشان نداد.

نتیجه کلی

بخش دریافت از نظر هسته داده و کنترل کانتینر قابل‌اعتماد است، اما هنوز کاملاً منطبق با سند و آماده بهره‌برداری واقعی نیست.

موارد مثبت

- اسکن واقعی و الزامی کانتینر
- کنترل وضعیت، قفل، ظرفیت و نشست فعال
- محاسبه صحیح وزن خالص با tare
- پشتیبانی درست از ظرف یک‌بارمصرف
- محاسبه خودکار هفته برداشت
- اعتبارسنجی محصول، گرید و سایز
- ثبت تاریخچه وزن، device، session و audit
- دریافت چندسبدی، persistence و انتقال کانتینری
- ایجاد خودکار وظیفه انتقال به سردخانه
- چاپ اختیاری لیبل دائمی سبد

شکاف‌های باقی‌مانده

1. دکمه «چاپ سبد جدید» برای اپراتور واقعی کار نمی‌کند.

این دکمه مسیر /api/containers را فراخوانی می‌کند که مجوز storage:write می‌خواهد، اما RECEIVING_OPERATOR این مجوز را ندارد. بنابراین اپراتور دریافت با خطای 403 مواجه می‌شود.

2. وزن رسمی از نظر backend به ترازوی فیزیکی متصل نیست.

سرور عدد ارسال‌شده توسط client را قبول می‌کند. پنل وب ورود دستی وزن دارد و ترمینال نیز دکمه دائمی «شبیه‌سازی وزن» دارد. در نتیجه اثباتی برای stable بودن خوانش یا منشأ آن از ترازوی ثبت‌شده وجود ندارد. این وضعیت با بند 2.12 سند فاصله دارد.

3. state machine دریافت ناقص است.

سند مسیر DRAFT → RECEIVING → RECEIVED → AVAILABLE و امکان لغو با دلیل را تعریف کرده است، اما کد بچ را مستقیماً با وضعیت RECEIVED ایجاد می‌کند. endpoint رسمی برای cancel کردن delivery/receiving و ثبت علت نیز وجود ندارد.

4. هشدارهای دریافت ناقص‌اند.

هشدار اختلاف وزن در دامنه وجود دارد، اما UI مقدار expected weight را ارسال نمی‌کند. علاوه بر آن tolerance از درخواست client قابل تعیین است، نه الزاماً از تنظیمات مصوب سیستم. هشدار تحویل تکراری، زمان خارج از شیفت و نزدیک‌شدن سبد به سرویس دوره‌ای نیز پیاده نشده‌اند.

5. مدل تأمین‌کننده ناقص است.

مدل فعلی فقط code، name و status دارد. اطلاعات تماس، منطقه و مرجع تسویه‌ای که سند مشخص کرده ذخیره نمی‌شوند. ساخت تأمین‌کننده جدید نیز مستقیماً در جریان دریافت در دسترس کاربر مجاز نیست.

6. یک اختلاف نیازمند تصمیم تجاری وجود دارد.

سند اصلی می‌گوید هر سبد باید هویت Receiving Batch مستقل خود را حفظ کند، ولی completeDelivery() بچ‌های سبدها را CONSUMED کرده و یک DELIVERY_AGGREGATE می‌سازد. این رفتار از نظر فنی منسجم است، اما انطباق دقیق آن نیازمند تأیید رسمی کسب‌وکار یا اصلاح سند است.

جمع‌بندی

دریافت فعلی برای سناریوهای آزمایشی مناسب و از نظر persistence قوی است. برای بهره‌برداری واقعی، برطرف‌کردن مشکل مجوز «چاپ سبد جدید» و اتصال غیرقابل‌دورزدن وزن به ترازوی فیزیکی، بالاترین اولویت را دارند.

این بررسی فقط read-only بوده و هنگام تهیه آن هیچ تغییری در کد، داده‌ها یا تنظیمات عملیاتی ایجاد نشده است.
