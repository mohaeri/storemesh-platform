# Fix Request coordination folder

This folder replaces copy-pasting Fix Request documents by hand between Mohamad, Claude, and Codex.

## Instructions for Codex (copy this block as your standing prompt)

> Every 20 minutes, check the folder `storemesh-platform/docs/fix-requests/open/`.
>
> - Look at the files in `open/`. Pick the **lowest-numbered** file you have not already started or finished. The number is the priority order — always work in order, don't skip ahead.
> - If you've already finished every file currently in `open/` and nothing new has appeared, do nothing and check again in 20 minutes. Don't start work that isn't explicitly placed in this folder.
> - Implement the Fix Request exactly as written: same rules as every round so far — real PostgreSQL tests (`DATABASE_URL` set, `# skipped 0`), update `storemesh-contracts` if the request changes a route/request/response shape, ship the web UI in the same round, don't commit or push mid-work.
> - When you finish the **entire** Fix Request (all Parts, committed and pushed), write your completion report as a new file in `storemesh-platform/docs/fix-requests/done/` with the **exact same base filename** as the one in `open/` (e.g. finishing `open/26-packaging-architecture.md` → create `done/26-packaging-architecture.md`). Do not edit or delete the file in `open/`.
> - Report format in `done/`: results per Part, real `node --test` output (pass/fail/skipped counts) for every affected repo (backend/web/contracts/terminal), commit SHAs and PR links per repo, and a note confirming the working tree is clean.
> - If a Fix Request's instructions are unclear or you hit something that needs a decision you're not sure about, stop and write what you found as a file in `done/` anyway (same naming rule), describing the blocker — don't guess on anything ambiguous.

## How the other two sides work

- `open/` — Fix Requests ready for Codex to pick up, numbered in priority order. Claude keeps this stocked with fully-designed, already-approved work — items that don't need a new decision from Mohamad.
- `done/` — completion reports. Claude checks this folder every ~20 minutes; a new or changed file here is treated as "this one is finished, go verify it." Claude independently re-runs the full test suite against real PostgreSQL, reads the actual code diff against the original request in `open/`, and reports the result to Mohamad.
- `needs-decision/` — fully-drafted proposals that need a real business or architecture call from Mohamad before they can become a numbered item in `open/`. Claude keeps drafting these in the background whenever `open/` is running low, so there's always something ready the moment Mohamad approves it — but Claude does **not** guess on these or promote them to `open/` on its own. When Mohamad reviews one and gives a decision, Claude turns it into a numbered `open/` file and moves the source doc (or a note) into `done/` or deletes it from `needs-decision/` as appropriate.
- `queued/` — Fix Requests that are fully drafted and already approved (no decision needed from Mohamad) but deliberately withheld from `open/` because they depend on an earlier, still-in-flight request finishing first. This is the real per-request review gate: Codex only ever reads `open/`, so a request sitting in `queued/` is genuinely invisible to it — unlike an in-progress note or interim report, which Codex has no mechanism to pause for. Claude moves a `queued/` file into `open/` only after independently verifying the request it depends on in `done/` against live code and real-Postgres tests. Use this whenever a Fix Request would otherwise bundle two or more independent fixes as "Parts" of one request — split them into separate numbered requests instead, release the next one only after the previous is verified done. Reserve genuine multi-Part requests (kept as Parts within one `open/` file) for the rare case where a later Part cannot even be specified or tested without an earlier Part's shipped code/schema to build on — and even then, Claude reviews the uncommitted work-in-progress directly (reading the live diff and running whatever tests exist) whenever checking status, since there is still no real pause-and-approve point between Parts of a single request.

**Standing mode as of 2026-08-27**: Claude works continuously — when `open/` empties out, it re-scans the codebase against the remaining review backlog for the next closeable Fix Request (mechanical, no new decision needed) and adds it directly to `open/`, and separately drafts `needs-decision/` items for anything that's genuinely a business/architecture call. It does not wait idle for Mohamad's input on those — it keeps working on whatever's next in the closeable queue while decision items sit in `needs-decision/` for whenever Mohamad checks back.

**Standing buffer rule as of 2026-08-30 (Mohamad's explicit instruction)**: Claude keeps at least 3 Fix Requests sitting in `open/` that Codex has not yet finished, at all times — not just when it happens to hit zero. Whenever a `done/` report drops the unfinished count below 3 (count `open/` files whose base filename has no matching `done/` file yet), Claude drafts enough new ones in the same check to bring it back to 3+, using the same re-verify-against-live-code-first method as every other round. This is a standing check on every status pass, not something Mohamad needs to ask for again.

**Clarification as of 2026-09-02 (fixing a recurring bug in this process itself):** "Do not edit or delete the file in `open/`" above applies to **Codex** only — Codex must never touch `open/`. It does not apply to Claude. Once Claude has independently verified a `done/N.md` completion report against live code and a real PostgreSQL test run, Claude deletes the matching `open/N.md` file. `open/` must only ever contain Fix Requests with no verified `done/` counterpart yet — that is the whole point of it being the backlog-count source of truth for the buffer rule above. Leaving a verified-done file's original request sitting in `open/` after `done/N.md` exists is not a valid "historical record" pattern; it happened twice (2026-08-27 through 2026-09-01, and again on 2026-09-02) and both times made the real backlog look 10-15x larger than it was, which is exactly what the buffer rule above exists to prevent being wrong about. If a historical record of the original ask is wanted, it belongs restated inside the `done/N.md` report itself (which the existing report format already effectively includes), not as a second copy of the file left in `open/`.

**Root cause found 2026-09-02:** the "recurring bug" above may not have been Claude skipping the deletion step — the connected `storemesh` folder (this whole repo tree, as mounted into Claude's sandbox) does not support deleting or renaming files once written. Every `rm`/`mv` on a file under `docs/fix-requests/open/` returns "Operation not permitted", including on a scratch test file created and immediately rm'd in the same session — so it's a property of this specific folder mount, not a one-off glitch. Plain scratch space elsewhere in the sandbox (e.g. `/tmp`) deletes files normally, and creating new files or overwriting existing file *contents* inside `storemesh` both work fine — it's specifically unlink/rename on this mount that's blocked. So a past Claude run may genuinely have tried and failed silently, or the tooling available in a given run may not surface `rm` failures clearly. Until this is fixed (or a run confirms it now works), Claude's verify step overwrites a verified `open/N.md` with a short "VERIFIED DONE — superseded by done/N.md" stub instead of deleting it — same effect for the buffer count (already keyed off `done/` matches, not file presence), but it's honest about not being an actual deletion, and it stops the file being mistaken for a live request if someone reads `open/` directly.
